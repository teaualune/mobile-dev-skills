## How the wording got there

Four full runs and three targeted ones:

- **S3** (the first wording, $7.97) failed four runs:
  - **`mono-cross-part-noparent` 1/3.** With no project workflow to turn to, the model planned all three parts itself, then wrote its own delegation brief for `feature-workflow`. The description allowed it ("invoke it yourself only to hand over an app's part of a cross-part feature with a delegation brief"). It now admits only a project skill's hand-over, and the body says a brief never comes from the model.
  - **`intake-requirements-dump` 2/3.** The missing run listed the gaps itself in one turn, without a skill.
  - **`intake-new-feature` 2/3.** The trace wasn't kept.
- **S3b** (the workflow wording fixed, "Asks follow-ups for what's missing" back in intake, $7.72): 78/78.
- **S3c** (after the review: the workflow description also admits a request that names the workflow; `workflow-named` and `no-workflow` added; $8.68) failed three intake runs.
  - **`intake-new-feature` 1/3.** Two runs explored first, found the fixture's saved `reading-history` sheet with every field filled, and invoked `feature-spec` to write its spec.
  - **`intake-requirements-dump` 2/3.** The one-turn answer again.
- **S3d.** Intake's description went back to its 0.3.20 wording ("the user wants to add a feature, describes one they're planning … Asks targeted follow-ups for what's missing."), keeping only the new monorepo sentence. Then 15/15 on the intake cases, matching 0.3.20 run beside it, and 12/12 on the monorepo cases. The trims had cost intake its trigger words; they were the only descriptions that changed between the S3b/S3c and S3d intake results.

## Observations

- **The eval loads only the plugin's skills.** A fixture's `.claude/skills/` isn't listed, so `mono-cross-part` can't grade that the project's `cross-part-feature` skill fired. In every `mono-cross-part` run the model found the skill file with a search, read it and followed it; in `mono-cross-part-noparent` it worked the request out itself.
- **`mono-delegate`** passes a brief that the user pastes, which the description's "a project skill tells you" doesn't strictly cover, since the eval can't list a project skill. It fired 3/3 in every state. In the probe run the model checked the brief (the app at `app/`, the spec folder inside it, the Flutter adapter) and tried to save `brief.md` first, which the eval's read-only tools refused.
- **`workflow-named`** fired 3/3: a request that names the workflow now runs it, where 0.3.20 was blocked by Claude Code (the review's live A/B). The `scaffold-*` cases ("Build it" for an approved spec) didn't start it.
