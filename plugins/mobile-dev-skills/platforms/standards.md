# Standards — all platforms

Rules for the code and tests the feature workflow writes, on every platform. The skills that write or review code load three files: this one, the platform adapter's `standards.md`, and the project's own `.mobile-dev-skills/standards.md` when it exists. Native code a feature writes for another platform, and its native unit tests, also follow that platform's native adapter's `standards.md`, when there is one. A project rule wins over a bundled rule it names.

- **The project's file** uses the same two headings, `## Code` and `## Tests`. A rule there that replaces a bundled one names it by its bold title, as in `- Replaces **Refreshable scroll view skeleton**: …`; any other rule adds to the bundled ones. **Name** and **Anchor to host tests** can't be replaced, because the conformance check depends on them.
- **Its `## Workflow` part**, optional, holds no rules, so no review checks code against it. A `Skills: <skill>, …` line names the project's own skills (a TCA reference, say) to load before writing code, and `Pause after each task: yes` has the feature workflow stop after each Phase 2 task for the user's go-ahead. Where a project skill's advice differs from a standard, the standard wins.
- **A standard wins over an exemplar.** Where the project's own files break a rule, new code follows the rule; to keep the project's way, the user replaces the rule in the project's file.

## Code

- **Mirror the project's naming style.** If existing files are `saved_articles_repository.dart` (snake_case), don't generate `SavedArticlesRepository.dart` (PascalCase). If providers are suffixed `Provider`, don't switch to `Notifier`.
- **Match the project's import style.** Some projects use package imports (`package:app/...`), some use relative. Match.
- **Put user-visible strings where the project keeps them.** If it uses localization files, add each new string there, in every locale, instead of hardcoding it.
- **No new dependency without approval.** A package the manifest doesn't list is added only after the user approves it.
- **Provisional shapes**, when the spec marks an entity, endpoint or field provisional because the API isn't built yet:
  - Every field on the provisional entity gets a `// TODO(api): provisional — confirm with backend` comment.
  - The entity class itself gets a class-level comment block stating it's provisional, when it was decided, and that JSON keys may need to change.
  - The repository is a stub implementing the same interface and returning hardcoded sample data after a simulated network delay (the platform's standards give its form). Name it `StubExampleRepository`, and place it next to the real repository file (`example_repository.dart` → `example_repository_stub.dart`) or in the project's `stubs/` folder if it has one.
  - Whatever provides the repository is wired to the stub, with a `// TODO(api): swap to real repository when backend is ready` comment above it.
  - A provisional field on a confirmed entity, for an endpoint that already exists, gets the `// TODO(api): provisional — confirm with backend` comment on that field and its mapping only. There is no stub: the real repository stays wired.
- **Native code behind an interface.** Shared code reaches each native interface of the spec's section 4, and each permission request in its permissions table, through one class, provided the way the project provides its repositories, so tests can fake it, a denial included. Native code does only what section 4 states.

## Tests

- **Where.** Test a scenario at the layer where its THEN lines can be observed: a screen state or user action in a test of the screen (on a platform whose standards say its screens have no host-test harness, a test of the state holder the screen renders), a request's mapping and error cases in a repository test, an invariant or a rule about data in the state primitive's test. Mirror the project's test layout and helpers.
- **Name.** A test's description starts with the requirement id and the scenario title, exactly as the spec writes them: `saved-articles.1 Empty`. Add words after the title only to tell several tests of one scenario apart. Write the description as one plain string literal, not split into a `group` name and not interpolated, so a text search for the anchor finds it. Keep the title unescaped; the platform's standards say how. Where a platform's test names can't hold a character of the description (a JVM method name can't hold `.`), its standards give the name form that stands in for the literal. The `test` anchor holds the description's text as the test file writes it, without the quotes or backticks around it. A section 6 still in the bullet format has no ids: there the description is `<Screen> <state or action>`.
- **Assert.** WHEN (and GIVEN) is the setup. Each THEN and AND line is an expectation on what the spec names: the widget, the copy, the call, the event (in a test of a state holder, on the state and copy it gives the screen, as the platform's standards say). A scenario that still holds `TBD` gets a `// TODO(spec)` instead of a test.
- **Fake** the layer directly below the one under test: the repository for state and screen tests, the HTTP client (a mock, or a hand-written adapter) for repository tests. Use the project's mocking library when it has one, otherwise hand-written fakes. No test makes a real request. A provisional feature is tested the same way, with a fake of the interface its stub implements; the stub itself gets no tests.
- **Anchor to host tests.** A scenario's test lives in the adapter's host-test folder, or for native logic in the native unit-test target its "Native interop" names, where the verification run can execute it. Tests that need a device are extra: never a scenario's only test, and the closing notes list the command to run them.
- **Platform.** A scenario tagged `<!-- platform: <id> -->` is tested in a host test like any other, with the platform set as the platform's standards say. Native code is faked behind its interface; a test of the native code itself is extra, like a device test, except a native unit test of logic the adapter's "Native interop" tests natively, which anchors its scenarios.
