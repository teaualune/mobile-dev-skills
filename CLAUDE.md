# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A Claude Code marketplace for one **plugin**, `mobile-dev-skills`, bundling eight skills under `skills/`, in two independent families: a two-phase feature workflow for mobile apps (requirements → spec → approval → implementation; Flutter, native SwiftUI and native Jetpack Compose, through platform adapters) and a build & store-deploy pipeline (a build skill that runs the platform adapter's build script, plus a framework-neutral store uploader). It also ships seven agents under `agents/`, refined copies of ECC agents that the feature workflow calls for review and build fixes ("Vendored ECC agents"). The feature workflow's platform knowledge lives in adapters under `platforms/`, one folder per platform ("Platform adapters"). It contains no buildable app: the content is `SKILL.md`, adapter and agent prompt files plus template files (Dart, Swift and Kotlin reference material, and a build-script template per adapter that has a build) that are copied into target projects, never compiled or executed here. There are no build or lint commands; the nearest thing to a test suite is the maintainer's contract check ("Maintaining this repo"), beside the end-to-end cases in `TESTING.md`. Deployment is `/plugin install` (via the repo's own marketplace manifest) or manually copying folders from `skills/` into a target project's `.claude/skills/`, with `platforms/` beside them for the feature workflow and the build skill, and `third_party/`, the agents and the license files for the feature workflow ("Plugin folder").

The plugin lives in `plugins/mobile-dev-skills/`, the **plugin folder**, which is all an installed plugin gets ("Plugin folder"). Its manifest is `.claude-plugin/plugin.json` there; the root's `.claude-plugin/marketplace.json` lists it. Paths in this file that start with `skills/`, `agents/`, `platforms/` or `third_party/`, and `.claude-plugin/plugin.json`, `MIGRATION.md`, `THIRD_PARTY_NOTICES.md` and `DISCLAIMERS.md`, are in the plugin folder, and one that starts with a skill's name (`mobile-store-deploy/scripts/`) is in that skill's folder. The target project's own paths (`.mobile-dev-skills/`, `scripts/build-version.sh`) are named as such; every other path is from the repo root. The plugin's README is `plugins/mobile-dev-skills/README.md`, the plugin README; "README" alone is the root one.

### Verifying a change

The only end-to-end check is loading the checkout as a plugin from a real Flutter, SwiftUI or Compose project and invoking the skill:

```bash
cd /path/to/an-app && claude --plugin-dir /path/to/mobile-dev-skills/plugins/mobile-dev-skills
# then: /mobile-dev-skills:feature-workflow …
```

`TESTING.md` lists those end-to-end cases, each with the evidence of the runs that passed it: a session that covers a case adds its evidence there, and a problem no case covers becomes a new case. The owner-only `/testing-intake` skill takes those sessions' side-check reports into it ("Maintaining this repo"). Its "Leaving alpha" says when the plugin leaves alpha.

`claude plugin validate .` checks the marketplace manifest and `claude plugin validate plugins/mobile-dev-skills` the plugin's (including the `userConfig` schema) statically; their missing-marketplace-description and missing-icon warnings are expected.

`python3 -I .claude/skills/maintainer/scripts/check_contracts.py` checks the deterministic part of the cross-file contracts and conventions below:
- script and JSON syntax, and hidden or bidi Unicode;
- skill frontmatter and description budget, counts, and the Intake Sheet sections;
- plugin-option lines and their restated defaults, substitutions, file references in each SKILL.md, and the headings a skill's files, the plugin README and the migration guide cite in a skill or file (`` `feature-spec`'s "Quality check" ``);
- manifest consistency, and the release stage: the version's form; while it says `-alpha.`, the `Alpha. ` description prefix and the alpha notices in both READMEs, `TESTING.md` and the migration guide, and none of them after; links to this repo's files on GitHub; and `TESTING.md`'s case rows, their evidence and "Leaving alpha" (`release`);
- the plugin folder: its files, the `LICENSE` copy, symlinks, and no `../`, link or repo-only path that leaves it or a manual copy;
- the vendored ECC files: manifest entries, notice comments, `THIRD_PARTY_NOTICES.md`, agent frontmatter and the agent-description budget;
- the platform adapters: their sections, check table, agents and referenced files, and every line of the adapters, the standards, the templates and the agents' Inputs sections (exact pins, see `maintenance/anchors.json`'s `_doc`);
- every line of the skills' rule-bearing text (the `rule-text` contract and the mode files): `feature-workflow`'s hard gate, Resuming, Step 0, Step 1.6 and Steps 2.2–2.4, `feature-spec`'s section 6 rules, quality check, update rules and Handoff, the scaffold's Tests, Spec anchors, Step 5 and Hard rules, and the whole of `feature-verify`, `feature-spec-compact`, `review.md`, `baseline.md`, `diagnose.md`, `reading.md`, `missing-tests.md`, `delegated.md` and `conversion.md`, so an added line that contradicts a rule fails. After an intended edit, `check_contracts.py --pins <file> [--heading "<heading>"]` prints the check to paste back, with the existing check's `min_len`;
- the build-script interface, and deploy-script exit codes, keys and arguments;
- the sibling plugins: which files may name each, the offer only when its skill is listed and the hint when it isn't, no name in a description, and the plugin README's rows and install lines (`siblings`);
- the spec checker's interface: its keys, exit codes, flags and finding kinds, and the callers that run it;
- Flutter wording in the framework-neutral uploader, platform words in the process skills, the pre-rename plugin, skill and state-folder names outside the migration guide, the READMEs' pointers to it and the legacy-folder rule, and pre-release versions or the improvement branch's work folder in shipped text and the docs (`mentions` rules);
- required wording, table rows, ordering and matching values (`maintenance/anchors.json`);
- `skills/`, `agents/`, `platforms/`, `third_party/`, `.claude-plugin/`, `plugins/`, `maintenance/` and maintainer paths, and links, in this file, both READMEs, ROADMAP and the maintainer skill.

Run it after every change; it must end with `fail=0 warn=0` (`KNOWN` lines are warnings the owner already decided on).

Root `analysis_options.yaml` excludes `**/*` from the Dart analyzer **on purpose**: `platforms/flutter/templates/*/*.dart` import packages this repo doesn't depend on (there is no `pubspec.yaml` here) and declare `part 'example.freezed.dart'` files that will never exist. They are prompt material, not compilable code — don't "fix" the templates to satisfy an analyzer, and don't narrow the exclude.

## Architecture — how the skills chain

### Feature workflow

`skills/feature-workflow/` is the orchestrator. The user starts it, with its command or by naming it; otherwise the model may invoke it only for a delegated run (a project's own workflow handing over an app's part of a monorepo feature), which its short description says. It drives the other four, which are model-invocable sub-skills:

1. **`feature-intake/`** — interactive requirement gathering. Its output contract is the six-section **Intake Sheet** (Summary, Routes, Affected screens, Entities & APIs, Binding logic, Figma references), whose fields also hold the answers to its non-functional topics. The sheet is saved to the target project's `.mobile-dev-skills/` as answers arrive ("Workflow state files").
2. **`feature-spec/`** — turns the populated Intake Sheet into a ten-section spec document (`<feature-slug>-feature-spec.md` by default; the orchestrator overrides location/naming to match the target project's docs conventions, and on its own the skill saves beside the project's spec index or existing specs, following their naming). Its §6 is written as Requirement/Scenario blocks with stable ids, and its quality check runs before every approval question; `feature-spec/scripts/check_spec.sh` decides the check's mechanical part. `feature-spec/conversion.md` holds the rules for converting an older spec, or a project's freeform feature doc, to that format.
3. **`feature-scaffold/`** — generates the code and its tests from the approved spec, in the adapter's dependency order (Flutter: entities → repository → native interfaces → state primitives → widgets → screens → routing → platform declarations → edits to existing screens, each layer's tests right after it), applying the standards ("Standards"), then fills the spec's `enforced`/`test` anchors. It mirrors the target project's own files first; the adapter's template sets (Flutter: Riverpod + go_router + Dio only) are the fallback.
4. **`feature-verify/`** — the conformance check: whether each requirement's `enforced` anchor still exists in the code, and each scenario's `test` exists and passes. It fixes nothing; its one write is the spec's `Last verified` line, with the index row's copy, after a full pass. The orchestrator runs it as the last check of its verification run, and it is model-invocable on its own for any spec with §6 blocks.

One more feature skill sits **outside the orchestrated chain**:

- **`feature-spec-compact/`** — standalone maintenance for existing spec files: folds accumulated change records (changelog sections, addenda, phased deltas, inline update notes) back into the base sections so only the current state remains. Its one hard gate is the mandatory Step 2 question — the caller decides whether removed history is discarded or extracted verbatim to `changelogs/<feature-slug>/<YYYY-MM-DD>.md` in the spec's folder, one file per compaction date (an older single `<spec-basename>-changelog.md` stays untouched) — and it must never alter the spec's meaning or section structure.

The orchestrator's Step 0 sizes each request (trivial, small, standard or large) and runs as much of the chain as that size needs. A trivial tweak skips all four sub-skills for an approved change plan, a small change gets only the questions it needs and a lighter spec or an update, and a large feature is split after intake into sub-features with a spec each.

An edit to a feature that was never specced starts with a **baseline spec**: a subagent following `skills/feature-workflow/baseline.md` reads the feature's code within a file budget, from the adapter's "Code entry points", and records what it does today as the spec that the change then updates.

Three request types sit beside the sizes. A **bug fix** has a subagent following `skills/feature-workflow/diagnose.md` trace the report to its cause, corrects or adds the scenario (or names the one the fix restores), and reproduces the bug as a failing test before the fix. A **refactor** runs the tests and the conformance check before any code moves, changes only the spec's design sections, and ends with the same results. Each records its reason in the spec as a change record, which compaction removes or extracts once the change is built. **Missing tests** (`skills/feature-workflow/missing-tests.md`) adds tests for scenarios the spec already states and no test checks, writing only tests and anchors. Tests are never forced on the user: a new test can be skipped when delivery comes first (`test: none — <reason>`), and a missing-tests request adds it later.

Phase 2 ends with a verification run (the orchestrator's Step 2.3) and a review (Step 2.4). The verification run records codegen, l10n, analyze, format, tests and conformance, each as PASS, FAIL or SKIPPED in the run report, and a failing check blocks any "done" claim. The review runs in fresh subagents: a built-in pass against the project's own rules and the spec, plus second opinions from the vendored agents. An open review finding blocks "done" too.

The orchestrator keeps the workflow's state on disk in the target project (the saved stack, the Intake Sheet, Phase 2's task list and run reports, and a spec index), so re-invoking it on a feature resumes where the work stopped.

In a **monorepo** (the app beside other parts with their own manifests or specs), the app's folder is the project root: specs, index, state and commands stay inside it. A feature that spans the repository's parts (backend, web, app) belongs to the project's own workflow, which may hand the app's part to the orchestrator with a **delegation brief** (`skills/feature-workflow/delegated.md`); the run goes from intake to review as a direct request does and ends with a closing block the parent reads. A direct request that spans parts is pointed to that workflow instead.

The `Explore`, `Plan` and `general-purpose` subagents referenced by the orchestrator are built-in Claude Code agent types — nothing to install.

### Platform adapters

The feature skills are process: gates, intake, the spec skeleton, tasks, verification rules, review and compaction. What depends on the platform sits in `platforms/`, one folder per adapter:
- **`platforms/flutter/PLATFORM.md`** — the Flutter adapter: when it applies, the project layout and stack fingerprint, the stack layer and its fallback, the convention probes, the Detection report, where reading a feature's code starts, the fvm command rule and the check commands, the generation order, the spec notation, its templates, its native interop (the `ios` and `android` platforms, Pigeon or channels, where permissions are declared, native unit tests for logic that runs without the engine), its agents and its build adapter (`pubspec.yaml` version bookkeeping, the fvm rule passed in as `FLUTTER_CMD`) ("Platform adapters" contract);
- **`platforms/swiftui/PLATFORM.md`** — the SwiftUI adapter, for native iOS apps: the same sections, with an `xcodebuild` command rule (container, scheme, simulator), Swift Testing results read from the `.xcresult`, file registration for new files (synchronized folders, XcodeGen or Tuist, or a group-based project), screen scenarios tested on the view model, a build adapter whose script edits `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` (in the project file, an `.xcconfig`, or through `agvtool`) and archives with `xcodebuild`, and `Native adapter for: ios`, so its standards, agents and test commands also cover the Swift a Flutter run writes in `ios/`;
- **`platforms/compose/PLATFORM.md`** — the Jetpack Compose adapter, for native Android apps: the same sections, with a Gradle command rule (the wrapper, a module and a variant), Analyze as the Kotlin compile with `--rerun` plus Android Lint's XML report, anchored-test results read from the JUnit XML reports, screen scenarios tested on the JVM under Robolectric (on the ViewModel without it), JUnit 4 tests whose backtick names write the characters a Kotlin name can't hold, or warns about, as `_`, a Build adapter of `none`, and `Native adapter for: android`, so its standards, agents and test commands also cover the Kotlin a Flutter run writes in `android/`;
- **`platforms/standards.md`**, **`platforms/flutter/standards.md`**, **`platforms/swiftui/standards.md`** and **`platforms/compose/standards.md`** — the code and test rules for every platform, for Flutter, for Swift and for Kotlin ("Standards");
- **`platforms/flutter/templates/riverpod-gorouter-dio/`**, **`platforms/swiftui/templates/observable-urlsession/`** and **`platforms/compose/templates/viewmodel-navigation-retrofit/`** — one template set per adapter, the fallback when the project has no file of a kind to mirror;
- **`platforms/flutter/build-version.sh`** and **`platforms/swiftui/build-version.sh`** — each adapter's build script template, which `mobile-build-deploy` installs as the target project's `scripts/build-version.sh`.

`feature-workflow`, `feature-spec`, `feature-scaffold` and `feature-verify` read the adapter, the last two only the sections they need; `feature-intake` and `feature-spec-compact` need none. `mobile-build-deploy` reads its "Project layout" and "Build adapter", and "Commands" when "Build adapter" sends it there. The skills reach the folder as `${CLAUDE_SKILL_DIR}/../../platforms/`, which is the plugin's own `platforms/` in a plugin install and `.claude/platforms/` for a manual copy into `.claude/skills/`. Hybrid work (a Flutter feature with Swift or Kotlin code) uses one adapter, plus a native adapter's standards, agents and test commands for the native files (SwiftUI for `ios`, Compose for `android`). Adding a platform means adding a folder; [`ROADMAP.md`](ROADMAP.md) lists the candidates not yet built (React Native) and what each needs.

### Agents

`agents/` is auto-discovered like `skills/`. A plugin install names each agent `mobile-dev-skills:<name>`; a manual copy into `.claude/agents/` gives it the bare `<name>`, and the orchestrator accepts either. All seven are workflow-internal, and their descriptions say not to use them outside their step. Each adapter's "Agents" table names a reviewer and a build fixer:
- **`flutter-reviewer`** — Step 2.4's Flutter second opinion, every run;
- **`security-reviewer`** — Step 2.4's security pass, for every platform, when a run touches auth, requests, secrets, storage, permissions or deep links;
- **`dart-build-resolver`** — Step 2.3's build fixer, called once after two failed fixes of a Codegen, l10n or Analyze check;
- **`swift-reviewer`** — the SwiftUI adapter's: Step 2.4's platform pass in a SwiftUI app, and the native pass on the Swift files a Flutter run writes in `ios/`;
- **`swift-build-resolver`** — the SwiftUI adapter's build fixer: a Codegen or Analyze check in a SwiftUI app, or a Flutter run's Native build of `ios/`;
- **`kotlin-reviewer`** — the Compose adapter's: Step 2.4's platform pass in a Compose app, and the native pass on the Kotlin files a Flutter run writes in `android/`;
- **`kotlin-build-resolver`** — the Compose adapter's build fixer: an Analyze check in a Compose app, or a Flutter run's Native build of `android/`.

### Build & deploy

- **`mobile-build-deploy/`** — the **build skill**, platform-neutral: orchestrates a release by running the target project's `scripts/build-version.sh` (version bump + iOS archive and/or Android AAB), capturing the artifact paths, then invoking `mobile-store-deploy` with them. What depends on the platform comes from the adapter's "Build adapter" section: the script template, which build flags apply, the version bookkeeping, the command and its header line, the setup values, the artifact checks, and any older scripts or known issues. The build script itself lives **in the target project** — `platforms/<platform>/build-version.sh` is the installable template, adapted per project via the `Project config — ADAPT` block at its top (Flutter: app name, flutter command — the fvm rule unless pinned or passed in via `FLUTTER_CMD`, flavors (none for an app without them), each flavor's build arguments (entry point, defines), scheme/configuration naming, iOS target fallback, required privacy usage keys; SwiftUI: app name, project and workspace, a scheme and configuration per flavor, where the version lives, required usage keys, extra `xcodebuild` arguments). An adapter whose "Build adapter" says `none` gets no build: the skill says so and offers `mobile-store-deploy` alone.
- **`mobile-store-deploy/`** — framework-neutral uploader of already-built artifacts, whatever built them (iOS `.xcarchive` → TestFlight via `xcodebuild -exportArchive`, signed in with Xcode's saved Apple ID session or an App Store Connect API key from the environment or a gitignored `ios-api-key.json`; Android `.aab` → Play internal testing via the Play Developer API, with an assisted Claude-in-Chrome fallback). Renamed from v0.2.0's `flutter-store-deploy`; keep Flutter-specific wording out of it — the Flutter `.aab` path appears only as the default of `android.json`'s `aabPathTemplate`. Unlike the build script, its `scripts/` are executed **in place** via `${CLAUDE_SKILL_DIR}`, which Claude Code substitutes with the skill's own folder for plugin, project and personal installs alike. Per-project values live in the target project's `.mobile-store-deploy/` config, created by the skill's setup mode; the pre-rename `.flutter-store-deploy/` is still read when it is the only one present, and a project's own deploy-config folder under another name that holds `ios.json` or `android.json` is offered as the config, never duplicated. Model-invocable on its own for deploy-only requests, and for a request to submit a build for review, which it points to a submission plugin ("Store submission").

## Cross-file contracts (keep in sync when editing)

Several rules are deliberately restated in multiple skills; changing one copy without the others breaks the workflow:

- **The hard gate**: no code before explicit spec approval ("ok" alone doesn't count). Stated in `feature-workflow` and `feature-spec`'s handoff section. It holds at every size `feature-workflow`'s Step 0 assigns: a trivial request's change plan is its spec, and nothing is edited until the plan is approved; each sub-feature of a large request is approved and built on its own. A bug fix or refactor is a spec change like any edit, approved before its reproduction test or its first moved line; a bug whose scenario the spec already states gets an approval that names the scenario the fix restores. A missing-tests request's plan is approved before its first test. A delegated run's approval is still the user's, given in the run or with the other parts' specs in one message that names the app spec's file.
- **Stack detection + fallback**: the adapter says what to detect and how. For Flutter: state management/routing/HTTP/codegen from `pubspec.yaml` and sample files; fall back to Riverpod + go_router + Dio + freezed only when detection fails, and label every fallback explicitly. The test packages are detected the same way and fall back to `flutter_test` with hand-written fakes. The stack layer, its fallback, the convention probes and the Detection report (with its `Test packages` line and a `Flutter/Dart command` line decided by the fvm rule) live once, in the Flutter adapter; `feature-workflow` (Step 1.2) and `feature-scaffold` (Step 1) both run that detection and produce that report.
- **The fvm rule** (canonical copy — every restatement must match): decides how Flutter/Dart commands run. Policy `fvm_policy`: `never` → plain; `always` → fvm, stopping if fvm isn't installed; `auto` (default) →

  | `.fvmrc` at project root | `fvm` installed | Skills | `build-version.sh` without `FLUTTER_CMD` |
  |---|---|---|---|
  | yes | yes | `fvm flutter` / `fvm dart` | `fvm flutter` |
  | yes | no | ask, naming the mismatch; default plain | exit 1 before touching `pubspec.yaml` |
  | no | yes | ask; default plain | `flutter` |
  | no | no | plain, no question | `flutter` |

  Only `.fvmrc` pins fvm; a `.fvm/` directory doesn't (fvm 3 keeps it as a gitignored local cache, and fvm 2's `.fvm/fvm_config.json` is deliberately unsupported). Restated in the Flutter adapter (`platforms/flutter/PLATFORM.md`: "Commands", and the script's own behavior in "Build adapter"); implemented by `platforms/flutter/build-version.sh`. The skills apply the adapter's copy, each stating the policy's value: `feature-workflow` ("Platform commands", settled in Step 1.2 or a trivial change plan), `feature-scaffold` (Step 1; reuses the orchestrator's decision when invoked from it), `feature-verify` (used only when no caller or saved `## Command` line gives the command) and `mobile-build-deploy` (once, before the first script run). In the script a non-empty `FLUTTER_CMD` — a literal ADAPT value, else the environment — bypasses the rule, and the Flutter adapter's "Build adapter" has `mobile-build-deploy` pass its decision that way on every run. Whatever the command, the script exits 1 before touching `pubspec.yaml` when it isn't installed; `mobile-build-deploy` checks the header's `Flutter:` line after every run, and runs v0.2.0's script (empty `FLUTTER_CMD=""`, ignores the environment) only when that script's own `.fvmrc`-or-`.fvm/` pick matches the decision ("Older scripts").
- **Plugin options (`userConfig`)**: `.claude-plugin/plugin.json` declares `fvm_policy` (default `auto`) and `spec_language_rule` (default "Chinese text must be Traditional Chinese (zh-Hant) only, never Simplified."). Skills read each as `[${user_config.KEY}]` followed by a fallback that restates the default: a never-saved value stays a literal placeholder even when it has a `default` (verified with `--plugin-dir` on Claude Code 2.1.325), and manual copies get no substitution at all. Changing a default means changing `plugin.json` and every fallback. `spec_language_rule` is restated in `feature-workflow` (Step 1.5), `feature-spec` (guidelines) and `feature-spec-compact` (Hard rules), each exempting quoted user wording, which stays as the user wrote it; `fvm_policy` in `feature-workflow`, `feature-scaffold`, `feature-verify` and `mobile-build-deploy`. Adapters, standards and other supporting files get no substitution, so a rule there reads its option from the line in the skill that loaded it; an adapter that needs a new option adds a `userConfig` key and that line to each skill that runs its commands. Don't write the `${user_config.` prefix anywhere else in skill content — it gets substituted; nor a literal shell `${…}` expansion in skill prose, which goes in a script instead. `options` needs Claude Code ≥ 2.1.271.
- **Provisional API shapes**: the one exception to "never invent endpoints/fields" — applies only when the user says the backend isn't ready, or when a delegation brief's API contract is another part's spec still in `draft` (its shapes are taken from that spec, not proposed). Each skill defines its stage's handling (intake proposes and marks `PROVISIONAL`, spec marks sections and adds a confirm-with-backend checklist, scaffold generates stub repositories with `// TODO(api)` comments as the common standards' "Provisional shapes" rule says). A new field on an endpoint that exists is marked alone, in each of those files and `feature-workflow`: the endpoint keeps its path and its real repository, with no stub, and the field joins the spec's provisional list. An endpoint built but not deployed keeps its real repository too, with its release gated in section 8 until a test or a live check ends the provisional state.
- **Intake Sheet section names/order**: `feature-intake` defines them; `feature-workflow` Step 1.3 and the spec template's sections map onto them, and a delegated run writes its brief's app slice into them. Binding logic splits across §5 (state primitives, data flow, caching, offline and resume) and §6 (per-screen states, side effects and permission requests as scenarios, platform differences as scenarios with a `platform` comment, always-true rules as `### Invariant:` blocks, and behavior with a trigger but no screen of its own as requirements with `screen: none`). Its permissions and capabilities fill §4's `### Permissions & capabilities` table, and Entities & APIs' native interfaces fill §4's `### Native interfaces`.
- **Spec template structure**: `feature-spec` defines the ten-section layout; `feature-spec-compact` promises to preserve whatever structure a spec file uses (its fold rules reference the template's "N/A — don't delete sections silently" convention), so template restructures should be sanity-checked against the compact skill's Step 3. The `### Test plan` is a subsection of §10, not an eleventh section, and `### Native interfaces` and `### Permissions & capabilities` are subsections of §4; compaction keeps all three. A topic in §9 leaves its §4 subsection out, as it does its other template parts. The one addition the layout allows is an unnumbered `## Appendix — <title>` after §10, for material kept word for word for another team (a converted doc's edge-case table): the spec checker ignores it, and compaction keeps it as no change record.
- **Non-functional topics + spec quality check**: `feature-intake` and `feature-spec` list the same topics in the same order, each in a "Non-functional topics" table. Intake's table says when a topic is relevant and which Intake Sheet field holds the answer; the spec skill's says where the spec answers it. A topic that doesn't apply, or that the user cut, is named in §9 instead of being answered, never both; one that applies but was never answered is a §8 TBD. `feature-spec` defines the "Quality check" and runs it in its Handoff. It checks states, endpoint errors, action results, vague words, topics, block syntax and layout, and platform work (each §4 permission row complete, with a denial scenario; each native interface method typed, with its errors). The spec checker (below) decides checks 1 (states) and 6 (block syntax and layout), and reports the double answers of check 5 it can see (a topic §9 names that keeps its template part) as `layout`; the model does the rest. `feature-workflow` stops that Handoff after the save (Step 1.5). Its Step 1.6 runs the check first, then again whenever the spec changed, and asks for approval only after a run that finds nothing new and whose `RESULT=` line says `open=0`, quoting that line in the question and naming each existing spec the change edited, which the script also checks for findings in the blocks the change edited or added (their `open` counts don't gate it). Settled §8 items end in the English marker `— deliberately deferred` or `— declined`. Findings become §8 TBDs for the existing loop. Step 1.6 also reads the spec's state section and Test plan against the standards files, and a line that prescribes what a rule there forbids is a finding of the same kind, settled by changing the spec or, on the user's yes, replacing the rule in the project's standards file. Only four kinds are fixed in place: check 6 findings, check 5's double answers (the template part left out, or the §9 entry when the part states what the feature does), slips the Intake Sheet or the user's own words already answer, and topics that clearly don't apply. A finding is never settled by copying a sibling scenario; a §8 item may offer that as a proposal.
- **Requirement blocks (spec §6)**: `feature-spec` defines the syntax:
  - `### Requirement:` and `### Invariant:` blocks with `id`/`screen`/`entities`/`enforced` comments, and `#### Scenario:` blocks with a `test` comment; `screen: none` is a requirement with no screen of its own, placed before the invariants, with no states to check;
  - the `> Last verified:` line under the H1;
  - per screen, `Loading`/`Error`/`Empty`/`Success` scenarios, or `N/A — <reason>`;
  - a scenario that holds on some platforms only: a `<!-- platform: <id> -->` comment before its `test` comment, with ids from the adapter's "Spec notation".

  Ids (`<feature-slug>.<n>`) are never renumbered; a new block takes the highest id plus one, counting blocks the same edit removes. There's no stored counter, since additions go straight into the spec file. Anchors are `<path>#<Symbol>`, and `<path>#<test description>` for a `test`, whose other values are `manual — <reason>` (approved with the spec), `none` (existing behavior with no test) and `none — <reason>` (a test the user skipped, before approval or in Phase 2, which blocks no run). Phase 1 pre-fills `enforced` only for behavior already in the code, and a baseline spec or a conversion from bullets its `test` anchors too; an edit sets an altered scenario's bare `test: none` back to the placeholder. `feature-scaffold` fills the remaining anchors and the `Last verified` placeholder in Phase 2, and changes nothing else in the spec. `feature-verify` dates the line after a full pass and writes nothing else. `feature-spec-compact` folds changes into blocks without changing an id or the `Last verified` line. It numbers behavior a record adds without a block the same way, and never converts a pre-block §6 (the spec skill offers that conversion). A conversion, from bullets or from a project's freeform doc, follows `skills/feature-spec/conversion.md`, which `feature-spec`'s update rules, `feature-workflow` Step 1.4 and the migration guide cite: the layout brought to the ten sections first, a place for each kind of non-bullet text, and nothing added but what the checker needs and the anchors, with a behavior the code contradicts kept as written and listed as an `uncertain` §8 item. `feature-workflow` resolves §6 TBDs per scenario (Step 1.6), checks each screen's states before generating it (Step 2.2), and alone writes the anchors that its implementation subagents report. A trivial change plan (`feature-workflow` Step 0) edits only the spec text that states what changes, in its current format, with no conversion and no quality check; ids, anchors and `Last verified` stay. A keyword, key or placeholder change goes to every skill named in this bullet, and to the spec checker.
- **Baseline spec**: when edit mode (`feature-workflow` Step 1.1) finds no spec for the feature, a `general-purpose` subagent following `skills/feature-workflow/baseline.md` records the feature's current behavior as its spec before intake, and the change then updates it like any other spec.
  - **Reading.** The orchestrator finds only the starting files; the subagent starts at the adapter's "Code entry points" (Routes, Screens, Links, App-wide, Tests), samples the screens the change touches (a Standard or Large change also the feature's other screens), expands one link at a time, and stops at a budget of 15 source and 5 test files or after three files in a row that add nothing. The budget and the expand, tests and only-what-the-code-shows rules sit in `skills/feature-workflow/reading.md`, which the bug-fix diagnosis shares; `baseline.md` gives the start and the stop.
  - **Writing.** `feature-spec` ("A baseline of existing code") defines it: blocks only for behavior whose code it names, every `enforced` filled, `test` an existing test whose body checks the scenario, by its own description, or `none`, `> Last verified: never (implemented, not yet verified)`, and the gaps as §8 items with the fixed words `uncertain`, `Unplaced:` and `Not read:`. It follows the project's spec layout and language when Step 1.4 found them.
  - **Request.** Before the subagent starts, the orchestrator saves the request as `request.md` in the feature's state folder (type, the user's words quoted), so a session that ends during the baseline keeps it; a delegated run writes one too, pointing to its `brief.md`.
  - **Afterwards.** The user reviews it before intake and decides whether the not-read files are read now; `request.md` gets a `Reviewed:` line. It gets no index row until Step 1.5 saves the change (a missing-tests run: Step 2.4); until then, a resume finds it by its baseline items and a folder holding at most `request.md` (and a delegated run's `brief.md`), returns to that review or past it, and continues with the saved request, and the index's miss rule gives it no row. A later change that relies on a not-read file extends the baseline first ("Extending a baseline"), and the user sees what that added. A Large change splits into sub-features with specs of their own, and its changes to the existing specs' blocks are edited into those specs too (Step 1.1). Its items are open §8 entries, which compaction leaves as they stand.
- **Bug-fix, refactor and missing-tests modes**: `feature-workflow` defines them, in Step 0's "Request types beside the sizes" and the "Bug fix and refactor" and "Missing tests" sections after Phase 2. Each has its own steps in place of intake; none is ever trivial or split.
  - **Bug fix.** The report (steps, expected, actual), the spec found by Step 1.1 (a baseline spec first when there is none), then a `general-purpose` subagent following `skills/feature-workflow/diagnose.md`: it reads by `reading.md`, runs the scenario's anchored tests, names the cause and the anchored tests that assert the actual result, and judges the spec `states it`, `vague`, `wrong` or `not covered`. The spec change follows `feature-spec`'s "When updating an existing spec". Phase 2 writes the reproduction test before any fix, or rewrites an anchored test that asserts the bug to the approved THEN line; it must fail on the THEN or AND line the bug breaks, recorded as `tasks.md`'s `> Reproduction:` line (`manual — …` only when no host test can reach the bug or the user skips the test), and the scenario's `test` anchor names it. One that passes fixes nothing: the user settles whether the test (rewritten) or the diagnosis (run again; a new cause is a spec change, since the record names the cause) is wrong, or neither shows the bug. `feature-scaffold` ("Tests") restates the test-first rule.
  - **Refactor.** A baseline run (Tests and `feature-verify`) before any change; a failing test that covers the moving code, or a finding other than `no test` and `moved`, stops it. A bullet-format §6 is offered the conversion first, or the refactor runs without Conformance. Pin tests for the touched blocks' `test: none` scenarios unless the user declines; they pass on the untouched code before anything moves, recorded as `tasks.md`'s `> Pinned:` line. A spec change to the design sections only with §6 untouched, and the approval names any Conventions Report line the design departs from (updated in `stack.md`, or a deviation). Small steps with Analyze and the pinning tests after each, their results on the step's task line; tests that keep their expectations (`feature-scaffold` "Tests"); every moved anchor updated ("Spec anchors"). Step 2.3's Conformance passes only with the baseline's findings, less those closed. Tests-only coverage (no spec, baseline declined) approves a plan instead and leaves out the spec's parts.
  - **Change records.** `feature-spec` ("Change records") defines the one-blockquote record next to the change, labeled `Bug fix <date> — <title>` or `Refactor <date> — <title>`; a refactor's names the scenarios pinned and left unpinned. `tasks.md`'s `> Change:` line and the run report's heading quote the label. Resuming takes the mode from a `draft` or `approved` spec's newest record that no report heading names yet, or from that `> Change:` line. `feature-spec-compact` lists the kind and keeps the newest record while the spec's index row says `draft` or `approved` and no run report's heading quotes its label, since its change isn't built and the workflow still reads it; once the change is built, it removes or extracts it like any record. `review.md`'s check 5 reviews a run against it.

  - **Missing tests.** `skills/feature-workflow/missing-tests.md` holds the mode's steps, read once Step 0 names the type or a resume finds its `> Change: Missing tests …` line. A baseline run of Tests and `feature-verify`; a plan of the `no test` and `test missing` scenarios to cover, listed by what a regression would cost, approved in one message; tests written from the THEN lines that must pass on the code as it is (one that fails on a THEN line goes to the user, as a bug fix or out of the plan); only the host-test folder and the anchors written; no change record, and the index row's status left as it is (Step 2.4 copies only `Last verified`, or adds a baseline spec's row); another run's unticked tasks are finished first. Step 2.3's Conformance passes as a refactor's does, with every planned finding closed.
  - **Skipped tests.** The user may skip a new test, before approval or in Phase 2 (`feature-workflow` Step 2.2): its `test` becomes `none — <reason>`, Step 2.3's Conformance doesn't fail the run on it, and it goes under the run report's Follow-ups. An existing test of an altered scenario is still rewritten, a scenario with an anchored test keeps its anchor, and a refactor's pin tests are declined, not skipped. A skipped test stays a `no test` finding, so `Last verified` stays undated until it exists. `feature-spec` (§6 "Skipped tests"), `feature-scaffold` ("Tests", "Spec anchors", Step 5), `feature-verify` (step 3) and `review.md` (check 4) restate it.

  A change to the record's label, the `> Change:`, `> Reproduction:` or `> Pinned:` line or the diagnosis' verdicts goes to every file named here.
- **Delegated runs (monorepos)**: `feature-workflow` ("Delegated runs", whose steps are in `skills/feature-workflow/delegated.md`, read before Step 0 when a brief arrives or a `brief.md` is resumed) defines them; `feature-intake`, `feature-spec` and the plugin README ("Monorepos") restate their parts.
  - **Project root.** The adapter's Root is the app's folder, which need not be the working directory. Each adapter's Root line says so, and `feature-workflow` ("State files"), `feature-intake`, `feature-scaffold`, `feature-verify`, `feature-spec` (Handoff), `mobile-build-deploy` and `mobile-store-deploy` restate it where they resolve paths or run commands. Paths written into state files, specs and the index start there, except a spec's `Contract:` line, a saved brief and the closing block. Every subagent prompt and every agent's Inputs section gives the project root.
  - **Monorepo**: the project root isn't the repository's root, and another folder holds a part with its own manifest or specs (`feature-workflow`'s "State files", restated in `feature-intake`); one app in a subfolder isn't one. In a monorepo or a delegated run, the specs, the spec index and `.mobile-dev-skills/` sit inside the project root, and no skill writes outside it.
  - **Entry.** `feature-workflow` sets no `disable-model-invocation`, so a parent workflow can invoke it. Its description, which joins the always-listed total, limits the model to a request that names the workflow and to delegated runs, sending other requests to `feature-intake`; its body says the same, counting a project CLAUDE.md line that sends feature changes through it (by name, or as "the workflow" when no project skill is one) as the user asking, and that the model never writes a brief itself.
  - **The brief**: `Slug`, `From`, `Request` (`new feature`, `change`, `bug fix` or `refactor`; a missing-tests request isn't delegated), `App`, `Specs`, `API contract` (each spec with `approved` or `draft`, or `none`) and `Approval` (`here` or `with the other parts`), then `## App slice` and `## Other parts`. It is saved as `brief.md` in each state folder the run writes, before any other file: `<Slug>/` for a new feature, the changed app spec's own slug for a change, bug fix or refactor, a folder per spec. A returning brief is found by its `Slug` line, and a brief applies only until its run's specs are `implemented`. A new feature's or change's slice becomes its `intake.md`. Step 0 sizes the slice alone, and a delegated request is never trivial.
  - **Approval** `with the other parts` ends Phase 1 at the closing block (`awaiting approval`). The approval is then a message of the user's in the conversation that names the spec's file and comes after its last change; a contract approved since turns its provisional shapes into confirmed ones first, and the user approves that change.
  - **Closing block**: `## Handoff — <Slug>` with a `Spec` line per spec (or `none — tests-only coverage`), `Stage` (`awaiting approval`, `implemented` or `stopped at Step <n> — <why>`), `Verification`, `Review`, a `Report` line per run report and `Follow-ups`, paths from the repository's root, ending every reply that ends a delegated run. Cross-part checks come back as manual follow-ups.
  - **Cross-part requests** without a brief aren't taken: `feature-intake` and `feature-workflow` name the parts a request touches and point to the project's own workflow, or offer the app's part alone. `feature-intake`'s description excludes them.
  - **API contract**: `feature-spec`'s "API contract from another part" has section 4 state every shape the app uses, under a `Contract:` line citing the other part's spec; a `draft` contract's shapes are provisional.

  A change to a brief line, the closing block's heading or lines, or a `Stage` value goes to `feature-workflow`, the plugin README and `maintenance/anchors.json` together.
- **Workflow state files**: `feature-workflow` ("State files") defines them. All but the index live in the target project's `.mobile-dev-skills/`, at the project root the adapter defines (in a monorepo, the app's folder). A project that has only the pre-rename `.flutter-skills/` (from a pre-release build) keeps using it, read and written in place of `.mobile-dev-skills/`. When both exist, `.mobile-dev-skills/` wins, unless the old folder holds unfinished work (an `intake.md` without a `> Spec:` or `> Split:` line, a `tasks.md` with unticked tasks, or a `request.md` or `brief.md` whose spec has no index row yet): then the skills that write state (`feature-workflow`, `feature-intake`, the scaffold) ask which folder to use. No skill moves or deletes either. `feature-workflow` ("State files") states this, and `feature-intake`, `feature-spec`, `feature-scaffold`, `feature-verify`, `feature-spec-compact` and `review.md` restate it where they read or write the folder. It is not under `.claude/`, whose paths Claude Code 2.1.325 treats as sensitive, so writes there prompt even in acceptEdits mode.
  - `stack.md` holds the Detected Stack, the Conventions Report and the command decision (`## Command`). It is reused while its fingerprint matches; the adapter's command makes it (Flutter: `pubspec.yaml` and `.fvmrc` without the `version:` and `# android:` lines, through `git hash-object`). On a mismatch only the manifest is re-read, and detection runs only when the stack changed. The command decision keeps one line per set of the command rule's per-machine inputs. The "Saved stack" rules are restated in `feature-workflow` (Step 1.2) and `feature-scaffold` (Step 1); the scaffold adds the conventions.
  - `<feature-slug>/intake.md`: `feature-intake` writes it as answers arrive. A `> Spec: <path>` first line, added by whoever writes the spec from it (`feature-workflow` Step 1.5 or `feature-spec`'s Handoff), marks it finished. So does `> Split: <sub-slug>, …`, which `feature-workflow` adds when it splits a large request, after writing each sub-feature's sheet.
  - `<feature-slug>/figma/`: Figma frame exports that the Intake Sheet's references name, written by the export `feature-intake` offers ("Sibling plugins") once the user agrees.
  - `<feature-slug>/brief.md`: a delegated run saves its brief here, as given, before any other file; it makes a resumed run delegated ("Delegated runs" above).
  - `<feature-slug>/request.md` (Step 1.1): the request a baseline spec is written for, saved before the baseline subagent starts, with a `Reviewed:` line once the user has reviewed the baseline; a delegated run's says `- Asked: see brief.md`. It applies until the spec has an index row or the folder holds another file besides a `brief.md` ("Baseline spec" above).
  - `<feature-slug>/tasks.md` (Step 2.2) names requirement ids per task and holds the run's `> Baseline:` and `> Standards:` lines, and for a bug fix, refactor or missing-tests run its `> Change:` line (with a bug fix's `> Reproduction:` or a refactor's `> Pinned:`). `report.md` (Steps 2.3 and 2.4) holds one report per Phase 2 run, newest first, written whether or not the run passed; edit mode reads the newest one's deviations and follow-ups.
  - The spec index, `index.md` in the spec folder, holds one row per spec and is found by its header row. Its status (`draft`/`approved`/`implemented`) is the only state of its own, and `implemented` waits for a passing verification run and review; the existing specs a sub-feature edits ("A run's specs", derived from the pointers in their blocks and, in Phase 2, from the ids in the tasks) move through `draft`, `approved` and `implemented` with it, each with its own Conformance run; the other cells copy the spec, and the spec wins.

  The slug is the requirement-id slug, chosen at intake, or by intake's rule when a baseline spec comes first. Only `feature-workflow`, `feature-intake` and the scaffold (`stack.md`) write these files, plus `feature-verify` for the `Last verified` cell of an index row and the Figma export for `figma/`; subagents report. Stored state is limited to what the spec and code can't say, and each file says how a stale or missing copy is handled. An index miss falls back to the sweep. A block still at `enforced: (filled in Phase 2)` that no task names was added after the tasks, so it goes through Step 1.6 first, unless the tasks are a missing-tests run's, beside a change not built yet. Resuming (before Step 0) picks the step from these files, top row first, so a `draft` spec never resumes into Phase 2. A saved spec whose index row was never written resumes at Step 1.6 with the row added as `draft`. A trivial request writes none of these files, apart from a `## Command` line in an existing `stack.md`. The project's `.mobile-dev-skills/standards.md` ("Standards") isn't state: the user writes it, and a skill adds a rule only when the user accepts one. The project decides whether to commit `.mobile-dev-skills/`; the skills never edit `.gitignore` for it (the deploy skills only offer to ignore what must stay uncommitted: `mobile-store-deploy`'s API key file, a native project's `build/`). `feature-spec-compact` writes only the spec and its changelog; it reads the index row and the run reports, never writes them.
- **Tests, verification run and conformance**: one loop across four skills.
  - **Tests.** `feature-spec`'s §10 `### Test plan` says how each layer is tested. `feature-scaffold` ("Tests") writes a test for every scenario that isn't `N/A`, `manual` or skipped (`none — <reason>`), right after its layer. The common standards ("Tests") hold the naming: a test's description starts with `<id> <Scenario title>` as one plain string literal. Where a platform's test names can't hold the description's characters, its standards give the name form that stands in for the literal (Compose: ``fun `saved-articles_1 Empty`()``). The `test` anchor is `<path>#<that description>`, its text as the test file writes it without the quotes or backticks. `feature-verify` finds the test with the adapter's **Test-name search** ("Commands"), which the anchors a baseline or a bullet conversion writes are made to match. Native logic the adapter's "Native interop" tests natively (Flutter: logic that must run without the engine, under the Test plan's `Native unit` line) gets native unit tests in that platform's unit-test target, which follow the native adapter's test rules, so its test-name search finds them, and run with its commands.
  - **Verification run.** The adapter's "Commands" table gives the platform checks in this order: Codegen, l10n, Analyze, Format, Tests, Native build. `feature-workflow` Step 2.3 and the scaffold's Step 5 run them in that order, then Conformance (`feature-verify`), with the same sentence naming the order. The scaffold's copy applies only when it runs outside the orchestrator. Both copies carry these rules:
    - the same "Results" bullet: a result comes from the command's output in this run, and `SKIPPED` is only for a check that doesn't apply, so a check that couldn't run is a `FAIL`;
    - Analyze, Format and Tests pass when nothing is new against a baseline taken before the first code file (Step 2.2 records it in `tasks.md`; the scaffold keeps it in the conversation), and Native build only when its builds succeed, so a native build that fails at the baseline goes to the user before any native file is written;
    - Tests also runs, by the adapter's row, the native unit tests of each platform whose native tests the tasks write or the spec anchors, and both baselines name them; a platform whose native command rule stops on this machine goes on the manual checks (the adapter's "Commands"), as one Native build can't build does;
    - a FAIL is fixed without weakening the check (no loosened expectation, `skip` or suppression comment), and blocks "done".

    Step 2.3 adds the orchestrator's part: after two failed fixes of a Codegen, l10n, Analyze or Native build check it calls the adapter's build fixer (Flutter: `dart-build-resolver`; for Native build, the native adapter's, or none) once and re-runs the check itself. When that fails too, or after two failed fixes of another check, it stops, marks later checks `NOT RUN` and still writes the report; the index row stays `approved` and the Verification task unticked. A trivial change plan runs the checks its edit needs under the same rules, without the build fixer, Conformance, review or a report.
  - **Conformance.** `feature-verify` checks the whole spec and never fixes. It always runs the anchored tests itself, a native unit test with its native adapter's commands: a scenario passes only on that run's output, never on a reading of the test or on a caller's word. When a native adapter's command rule stops on this machine, its anchored tests go on the report's `Not run:` line (`<id> [<scenario title>] — <why>`), which isn't a finding but leaves `Last verified` undated. A description missing from a run of several files is run again with its file alone before it is `test missing` (the Flutter adapter's anchored-test command runs its files in one command with `--concurrency=1`, for the same reason). Its finding kinds are `not anchored`, `moved`, `unimplemented`, `test missing`, `no test` and `failing`; unspecified behavior and a contradicted THEN or AND line (its own step 6, which reads the run's blocks and files that the orchestrator passes in) are listed, with the line's `path#Symbol`, but aren't findings. Only a full pass writes `> Last verified: <date> (commit <sha>)`, and never while the index row says `draft`. A Phase 2 run fails only on findings in what it built (in an edit, the scenarios its tasks list), so older gaps, deferred TBDs and skipped tests become follow-ups. A refactor or missing-tests run instead passes only with its baseline's findings and no other, less those it closed. When `feature-verify` reports `no test` or `test missing`, it offers a missing-tests request once, as the user's call.

  A change to the test naming, a check's name or order, a finding kind or the `Last verified` format goes to every skill named here.
- **Review (Step 2.4)**: `feature-workflow` defines it, and `skills/feature-workflow/review.md` holds the built-in pass.
  - **Passes.** It runs after a passing verification run, only in fresh subagents that report and edit nothing. The built-in pass (a `general-purpose` subagent with `review.md`) checks the Conventions Report, the standards files and the spec's scenarios, and its closing line names the standards files it read. The adapter's reviewer (Flutter: `flutter-reviewer`) runs every time, unless the adapter names `none`; a native adapter's reviewer runs on the native code in its language a run writes for its platform; and `security-reviewer` when the run touches auth, requests, secrets, storage, permissions or deep links. Every pass gets the standards files' paths.
  - **Precedence.** The spec, the Conventions Report and the standards win. A second-opinion finding that contradicts them is a question for the user, never an edit.
  - **Settling.** Each finding ends as fixed, deviation, question, declined or follow-up. A CRITICAL or HIGH finding is declined or left as a follow-up only with the user's agreement, and its question stays open until answered. A fix goes back through Step 2.3 through Conformance, and one more review covers only the files it changed. A spec change the user chooses in answer to a question (or to a contradicted line) is their approval when it only brings the spec to what the code does and the question quoted its lines; any other goes through Step 1.6. Either way Step 2.3 runs again on every spec it touched. An open finding blocks "done", and the index row's `implemented` waits for the review.
  - **Record.** The run report's `### Review` quotes each pass's closing line, so a pass that didn't run shows; a pass that returns without one is started once more, then fails. It holds the first round's findings and settlements before any fix, so a resumed run continues with the second round.

  `review.md` names the standards sections it reads, so renaming one of them changes both files. What Step 2.3 and Step 2.4 pass to an agent is what that agent's Inputs section lists.
- **Platform adapters**: `platforms/<platform>/PLATFORM.md` is the only place a process skill gets platform knowledge.
  - **Sections**, in this order: Applies when, Project layout, Stack layer, Convention probes, Detection report, Code entry points, Commands, Generation order, Spec notation, Standards, Templates, Native interop, Agents, Build adapter. The skills cite them as `the adapter's "<Section>"`, so renaming one changes every skill that cites it. Each section carries the labels the skills read (`maintenance/anchors.json` lists them): Project layout's Root, Manifest, Source, Host tests, Generated files and Fingerprint; the Detection report's `Detected stack:` and `Detected conventions:` parts with their `Test packages` and `Exemplar` lines; Code entry points' Routes, Screens, Links, App-wide and Tests; Spec notation's section 4 native interfaces and permissions and its platform tags; Native interop's Platforms, Native adapter for, Mechanism, Native code, Declarations and Testing; Build adapter's Template, Platforms, Version bookkeeping, Command, Setup and Artifacts; the commands below.
  - **Commands.** The adapter's command rule, then a check table whose first column is Codegen, l10n, Analyze, Format, Tests, Native build, in that order, then the commands for a layer's tests, the test-name search and the anchored tests `feature-verify` runs, a new golden and device tests. The six rows are roles every platform maps onto: generated sources, generated localization, compile and static analysis, the formatter check, host tests (with a hybrid project's native unit tests), and the build of the native platform folders a run touches (`none` for a native app, whose Analyze already builds it). Native build passes only on successful builds, and a platform the machine can't build becomes a manual check, as does one whose native unit tests it can't run. A role the platform lacks has `none` as its command and `never` under "Runs when", so it is `SKIPPED`.
  - **Agents.** A table naming a Reviewer and a Build fixer, each a file in `agents/` or `none`, with the reviewer's closing line that Step 2.4 quotes. A reviewer reports severities CRITICAL, HIGH, MEDIUM and LOW, which Step 2.4 settles by. With `none`, the platform pass is `NOT RUN` and Step 2.3 has no build fixer to call.
  - **Lookup.** `feature-workflow`, `feature-spec`, `feature-scaffold` and `feature-verify` carry the same "Platform adapter" paragraph: grep every adapter's `## Applies when`, use the one the project meets, ask when several do, stop when none does. `mobile-build-deploy` carries the same lookup, asking which app to build. A sub-skill that `feature-workflow` invoked uses its adapter. The orchestrator and the scaffold read it in full, apart from "Native interop", which only a spec whose §4 lists native interfaces, permissions or capabilities needs; `feature-verify`, the spec skill, a trivial request and a chunk subagent read only their sections.
  - **Hybrid.** `feature-workflow` and `feature-scaffold` carry the same "Native adapters" paragraph. The adapter found by the lookup owns the feature; its "Native interop" lists the native platforms the project embeds (Flutter: `ios`, `android`), and native code for them follows that section. An adapter whose "Native interop" says `Native adapter for: <platform>` adds only its "Standards" and "Agents" to that platform's native files (a native reviewer pass in Step 2.4, the build fixer for a failing native build), and its "Commands" to the native unit tests the owning adapter's "Native interop" gives native logic there: its command rule on the container that section names, with a `## Command` line of its own in `stack.md`, and its commands for a layer's tests, the Tests check, the test-name search and the anchored tests (`feature-verify` finds the native adapter by that line for an anchor in a native platform's folder); without one, those files get none of these. Its standards and reviewer cover only the files in its own language, which that line names (Swift, Kotlin); native files in another language, such as an older project's Objective-C or Java, get no native review, and Step 2.4 records `NOT RUN — no reviewer for <language> files` on a Native row of their own; a failing native build still goes to the native adapter's build fixer. At most one adapter may claim a platform. A native adapter's "Applies when" excludes another framework's platform folders, so the lookup never offers it there.
  - **Templates** are named relative to the adapter's folder, and every one it lists exists. Templates and the adapter's own `standards.md` are optional; the "Templates" and "Standards" sections then say `none`. So is a build: "Build adapter"'s Template names `build-version.sh` in the adapter's folder, or says `none`. The scaffold's "Pattern sources" puts the project's own files first and the templates second.

## Conventions

- The bundle must stay **project-agnostic**. Concrete paths, commands, and doc conventions (e.g. `docs/specs/`, `.stg` flavor suffixes) are illustrative examples users may replace per the plugin README's "Per-project adjustments" — never hardcode a specific project's names or rules. **Configurable defaults** (keep the defaults): Chinese text in spec documents is Traditional Chinese only, and Flutter/Dart commands follow the fvm rule with policy `auto` — both are plugin options ("Plugin options" contract above), not hardcoded rules. For the deploy family, project-specific values belong in the target project (`scripts/build-version.sh`'s ADAPT block, `.mobile-store-deploy/`), never in the skills.
- **Versions.** Every change to the plugin folder bumps `version` in `.claude-plugin/plugin.json`, the only place the number is written: `0.1.0-alpha.N` while the plugin is in alpha (`TESTING.md`'s "Leaving alpha"). Claude Code updates an install whenever the string changes. Shipped text names only released versions (`v0.2.0`, `0.1.0-alpha.1`); the `0.3.x` builds were never released and appear only as evidence in `TESTING.md` and the eval results.
- Skill `description:` frontmatter doubles as the auto-trigger condition; each one also states what the skill must NOT be used for. Preserve that pattern when editing.
- Neither `.claude-plugin/plugin.json` nor `marketplace.json` enumerates skills or agents — `skills/` and `agents/` are auto-discovered, so adding a skill means adding a folder with a `SKILL.md` and nothing else, and adding an agent means adding its file (plus a manifest entry when it comes from ECC). What the manifests *do* carry (plugin `description`, `version`, keywords) duplicates README's framing; keep the skill and agent counts and the family split in sync across the plugin README, plugin.json, marketplace.json, and this file when a skill or agent is added or removed. None of the plugin's skills sets `disable-model-invocation`: all eight are model-invocable, and `feature-workflow`'s description limits the model to requests that name it and to delegated runs ("Delegated runs" contract). The project skills under `.claude/skills/` (the maintainer and `testing-intake`) aren't plugin skills and aren't counted.
- Platform knowledge (package names, commands, file patterns, the generation order, code rules, build scripts and version bookkeeping) goes in an adapter or its standards, never in a feature skill or the build skill. They name Flutter things only as examples ("e.g.", "for Flutter").
- Pre-rename names (the plugin, the five skills and the state folder renamed since v0.2.0) appear only in the migration guide ("Migration guide"), the READMEs' lines that point to it, and the legacy-folder rule ("Workflow state files"). The checker's `mentions` rules list them and fail anywhere else, so new text uses the current names.
- Template files are copied into target projects and adapted, not literal copy-paste output: `platforms/flutter/templates/riverpod-gorouter-dio/*.dart` (pairs for with/without codegen: `entity_freezed`/`entity_manual`, `provider_codegen`/`provider_manual`; `screen_test` shows the test naming), `platforms/swiftui/templates/observable-urlsession/*.swift` (`ExampleListViewModelTests` shows the test naming; `@testable import App` stands for the app's module; built and tested in a fixture project under Swift 6 with either default isolation before shipping, since nothing here compiles them), `platforms/compose/templates/viewmodel-navigation-retrofit/*.kt` (`ExampleListScreenTest` and `ExampleListViewModelTest` show the test naming; built and tested in a fixture project with the fallback stack before shipping), each adapter's `build-version.sh` (ADAPT block; the SwiftUI one archived in a fixture project in each `VERSION_SOURCE` mode before shipping), `mobile-store-deploy/templates/` (ExportOptions default + example project config). By contrast, `mobile-store-deploy/scripts/` and `feature-spec/scripts/` are executables run from the installed skill directory — keep them project-agnostic and non-interactive.

## Maintaining this repo

`.claude/skills/maintainer/` is a **project skill for the owner**, invoked as `/maintainer [contracts [full] | toolchain | packages | claude-code | ecc]`; with no argument it triages. It never loads for plugin users:
- project skills load only in sessions started inside this repo, or with `--add-dir` pointing at a checkout;
- a plugin loads skills only from its own `skills/`, and a marketplace install caches only the plugin folder. The marketplace's own clone of this repo (`~/.claude/plugins/marketplaces/`) still holds `.claude/`, `maintenance/` and `TESTING.md`, but nothing loads from it;
- `disable-model-invocation: true` keeps it out of the skill listing.

The project-agnostic convention doesn't apply to it. It is proposal-only: one evidence-backed diff per finding, applied only after the owner accepts it, never committed. Every finding cites a fetched source from the allowlist, or `file:line` for repo-internal drift. Deploy-script and template changes are applied only as "needs dry run" and stay uncommitted until the owner's dry run in a real project passes.

`.claude/skills/testing-intake/` is a second project skill for the owner, invoked as `/testing-intake <report file> …` with the path of each side-check report that a real-app session wrote (`~/.claude/MOBILE-DEV-SKILLS-E2E.md`); it loads and is guarded like the maintainer. It takes the reports into `TESTING.md`. The evidence and the new problems go in first. Then each new problem gets a fix or drop suggestion, the owner adjusts the list and approves it, and only then are the plugin edited, its pins re-pinned with `repin.py`, and the checks re-run. The owner is last asked whether to release the next `alpha.N`. Reports already taken in are listed in `maintenance/state.json` → `testing_intakes`.

Two guards are **best-effort by design**:
- the skill's `disallowed-tools` (commit, push, tag) lasts only for the turn that invokes it; after that, the proposal-only rule is the guard;
- the scripts enforce the URL allowlist, every redirect included, but the model's own fetches are held to it only by the skill's rules. A session-long hook could enforce it, at the cost of persisting after the run.
